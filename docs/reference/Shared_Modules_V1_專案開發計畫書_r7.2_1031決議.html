關鍵技術說明

  • TransactionRunner：所有寫入都包在交易內；遇到死結（1213）、鎖等待（1205）或序列化失敗（40001）最多重試 3 次；拒絕巢狀交易，避免外層 rollback 吞掉內層。
  • LockScope 鎖順序：L1 容量列（series 或 calendar_event）→ L2 member_states（依 id 排序）→ L3 family_links（共享鎖）→ L4 自己擁有的列（booking、charge）→ 最後才拿外部列的共享鎖。所有 Action 依同一順序，從根本消除死結。
  • 冪等：預約用 client_request_id（嚴格 UUID）＋唯一鍵；付款用 idempotency_key＋request_fingerprint（SHA-256），同一個鍵但內容不同就回 IDEMPOTENCY_CONFLICT。
  • generated column 唯一鍵：bookings.active_flag 只在有效狀態時有值，讓「同一會員同一場次只能有一筆有效預約」由資料庫保證。
  • Money：金額一律存整數分，運算用 App\Support\Money（cents、format、display），不使用浮點數。
  • Outbox：通知與業務在同一交易寫入，COMMIT 後才派送；用 dedupe_key 去重、SKIP LOCKED 並行、有限次數重試。
  • Presenter：JSON 欄位只有一個來源（Present.php），App 與文件契約一致。
  • 模組閘門：module:key middleware、AppResource::$module（Filament）、SkipIfModuleDisabled（Job）、outbox 通道過濾；V1 再補 Action 層的 guard 與 DRAINING 狀態。
  • integrity:check：每日檢查 14 條不變式（例如 member_double_seat、stale_makeup、欠費計數與實際一致）；V1 新增點數餘額＝流水加總、收藏上限。

核心流程

頁面 Registry／Manifest（程式碼管理） → 驗證頁碼、路徑及元件關聯 → 原子同步兩張索引表 → 管理員在 Filament 搜尋／篩選 → 查看簡易頁面、點擊跳頁或返回 → 複製除錯資訊並搭配 PNG 截圖 → 交給 ChatGPT／Claude。Flutter 只依既有會員權限顯示目前頁碼，不讀取整份 Atlas。

PA-SYNC-01：；新增 PA-SYNC-01：Claude 大批次完成 → Registry → 驗證 → Hash 差異 → CLI 同步／跳過 → DB → Filament，失敗回滾。

資料表

ui_pages：app_code、page_code（跨 App 複合唯一）、module_code、page_name、source_path、route、主要 DB/API 參照、版本／同步標記、retired。ui_page_components：ui_page_id 外鍵、component_key、type、label、field/action、db_column、target_page_code、sort_order。僅兩張核心表；不得擅增版本、截圖、Bug、Scenario 表。

API

管理員端使用 Filament／Laravel 已授權的後台讀取及索引同步流程；不開放公開 Page Atlas API。Flutter 沿用現有登入／me 回應中的 can_view_page_ids 權限（若目前尚無該欄位，需在既有契約擴充），不為每頁額外呼叫 API。資料表／API 對照未經程式核實須顯示「待核對」。

Filament 後台

獨立選單「Page Atlas 🔎」；搜尋頁碼、名稱、App、模組；頁面清單＋關鍵元件清單＋來源／DB／API 資訊；依元件資料產生約 80% 重要資訊的簡易示意圖；有 target_page_code 的按鈕可跳至另一示意頁並返回。提供一鍵複製頁碼、來源、元件、DB、API、版本及待核對事項；PNG 截圖須先驗證瀏覽器可行方案，保留手動擷取備援。僅授權管理員可進入。

PA-SYNC-01：；顯示最新同步時間、待核對項與停用頁面狀態。

Flutter App

正式 App 一般帳號不顯示頁碼；獲後端授權的 AdminTest 類測試帳號登入後自動顯示，不提供 App 內開關。共用 PageIdBadge 或既有 Router／Scaffold 統一掛載；SafeArea、IgnorePointer、避開返回鍵、輸入欄、播放器及底部導覽；無安全位置時可隱藏。登出／換帳號清除舊權限。App 不載入 Registry、Mock、DB/API 索引，也不額外增加專用請求。

PA-SYNC-01：；Flutter 不呼叫同步 API，也不以 JS 自動更新 DB。

規則、去重

永久頁碼不可重編、不可回收；以 (app_code,page_code) 保證跨 App 唯一。Registry／Manifest 是唯一權威，資料庫僅作索引；匯入前檢查重碼、失效來源及導航目標，失敗不得部分寫入。只登記關鍵元件，不重建像素級 UI；不加 Playwright、獨立 Preview Server 或大型新依賴；頁碼不代表授權，正式 App 不顯示程式路徑／DB/API。

PA-SYNC-01：；Manifest Hash 去重、整批驗證、交易回滾、顯式停用、禁止因批次缺頁而自動刪除。

驗收

① 不同 App 相同局部頁碼可正確區分、重碼拒絕；② 路由或檔名更改不重編永久頁碼；③ 後台可查詢頁面／元件／來源／DB/API，未知項標待核對；④ 簡易示意能跳頁、返回，且不執行正式寫入；⑤ 可複製完整除錯摘要，PNG 可取得或有明確可用的手動備援；⑥ 一般會員不見頁碼，授權帳號可見、不遮擋操作、登出清除；⑦ 同步失敗回滾；⑧ 未實際測試的項目不可標示通過。

  • T11 主金鑰輪替：建立新主金鑰（active）→ 背景逐批把 CEK 重新包裝（舊主金鑰 retiring 期間仍可解包）→ 全部完成且驗證後才把舊主金鑰標 retired；中途失敗可續跑、不刪舊版，既有離線授權與密文都不受影響
  • T12 內容金鑰輪替：正常輪替＝產生新版本密文與 CEK，新授權用新版本，舊版本進入 grace 期（後台設定），期間既有授權照常、到期後重連檢查回 rekey_required；疑似外洩＝舊版本立即標 compromised，停止核發舊版授權，重連檢查回 rekey_required，完全離線的裝置仍無法保證即時失效
  • T14 調降上限：上限由 2 改為 1 時不自動撤銷既有裝置，只阻止新增；後台顯示超額；管理員可指定撤銷某台裝置，必填原因並寫入稽核

來源：使用者提供《Shared Modules 重建計畫書 Claude v4.1 定案稿2》。保留原案具體規則供 V1 對照；與 V1 最新規格衝突時，不直接覆蓋，需逐項確認。此處是規劃／參考，不代表程式已實作或驗收。

6.1 預約狀態（booking.status）

付款狀態另外獨立，而且分成兩條軸（6.11）。應收：unpaid → paid；unpaid → overdue（逾期，只標記，不取消）；overdue → paid（補繳）；unpaid／overdue → void（預約被取消，尚未收款）。退款：none → review → partial／done／declined。預約狀態、應收、退款三者互不改寫，符合 PAYMENT-001。所有狀態轉換都採白名單，其他轉換一律拒絕。

6.2 預約流程（整期與單場共用）

  1. 驗證登入者 verified_status=2；若替家庭成員預約，驗證有效代管（資料庫鎖定讀取）。
  2. 用 client_request_id 查詢：已存在就直接回傳原結果（冪等）。
  3. 交易開始：鎖定容量權威列（series 或 calendar_event），驗證開放／截止時間和狀態。
  4. 鎖定 member_states：參加會員與付款人（代訂者）兩列，依 user_id 排序一次取得。檢查付款人的欠費計數（6.8），以及參加會員與已確認預約的時間衝突（6.6）。
  5. 依 D2 檢查有效預約，並依 6.7 的名額池判斷：有名額且沒有人在候補 → confirmed；否則候補未滿 → waitlisted（序號 = max + 1）；都滿 → 回傳 409 額滿。
  6. confirmed 且價格大於 0 → 建立 charge，due_at 依 6.3 計算。
  7. 同一交易寫入 outbox（預約成功、付款提醒）和 audit。提交。

6.3 付款期限公式（數值可在後台設定）

遞補的付款期限（Q14 已定案）：只在開課前遞補（整期以第一堂為準）。遞補當下：

這樣遞補者一定拿到一個「晚於現在、不晚於開課」的明確期限，並立即收到「候補成功，請於 X 前繳費」的通知；不會一轉正就變成欠費。開課後不再遞補，剩下的候補會由排程關閉（6.4）。

6.4 取消與遞補（v3：兩段交易）

  1. 取消交易：L1 容量列 → L2 付款人的 member_states → booking → charge。booking 改為 cancelled；charge 依 6.11 處理：未收款就改為 void（原本是 overdue 的話，欠費計數 −1）；已收款就維持 paid，並把 refund_state 設為 review，進入後台「待退款」，由管理員處理（M08-004：先取消、後退款）。同一交易寫入 outbox 和 audit，然後提交。遞補和補課清理都不在這筆交易內做。
  2. 遞補交易（PromoteWaitlist，每筆只處理一位）：L1 容量列 → 讀取 FIFO 第一位 → L2 這位候補者的 member_states（參加會員與付款人，依 id 排序）→ 重新檢查資格、代管授權、付款人欠費、與已確認預約的時間衝突、是否已開課 → 通過就轉正，並依 6.3 建立遞補帳單；不通過就取消並記錄 skip_reason（unverified、delegation_revoked、overdue、time_conflict）→ 提交。若仍有空位和候補，再開下一筆交易。
  3. 取消提交後，同一請求會立即呼叫 PromoteWaitlist；即使這一步失敗，每分鐘的排程也會掃描「有空位且有候補」的對象補做，並且冪等。
  4. 空位不會被插隊：新的預約只要看到還有人在候補，就只能排入候補（6.2 第 5 步）。
  5. 會員只能在 cancel_closes_at 之前取消；代訂者取消時，會重新驗證代管授權。重送取消請求 → 回傳 replayed=true。
  6. 開課時關閉候補：排程在單場開始時（整期為第一堂開始時），把剩下的 waitlisted 改為 cancelled，skip_reason = waitlist_closed，並發送通知。

6.5 出席、請假、缺席、補課（R1.59 第八章）

  • 簽到：QR 掃描或工作人員代簽，寫入 attendance=present。只有 confirmed 的預約可以簽到，候補者不行。
  • 請假：會員在開課前（【需決定】Q3：截止時間）透過 API 請假，寫入 leave。
  • 缺席：排程每小時找出「已結束超過 1 小時、absence_closed_at 為空」的場次，對沒有紀錄的應到者寫入 absent，再設定 absence_closed_at，所以重跑不會重複寫入。
  • 更正：管理員可把 absent 改為 present 或 leave，必填原因並寫入稽核；爽約次數會即時重新計算。
  • 補課：管理員對某筆 leave 或 absent 紀錄執行「核准補課」，選擇目標場次，系統建立 type=makeup 的預約，占用該堂的 makeup_capacity，並且只能使用一次（同一筆來源出席紀錄只能被一筆有效補課預約引用）。

6.7 名額池與補課容量（v3：共用場次也不會超賣）

一般單堂與補課共用一個場次時，兩個池加總不會超過實體座位，而且每次占位都會再檢查實體上限，即使管理員事後調整也不會超賣。補課的來源（一筆 leave 或 absent 出席紀錄）由 UNIQUE(makeup_of_attendance_id, active_flag) 保證只能被一筆有效補課引用。

6.8 欠費規則（Q1、Q12 已定案；v3 處理並發）

  • 欠費者 = 負付款責任的人：charges.payer_user_id（就是代訂者；代自己訂時就是本人）。名下有 overdue 帳單的人，不得新增付費預約，也不得加入付費候補，回傳 PAYMENT_OVERDUE。家庭成員本身不付款，所以不會因為「家庭成員欠費」而限制到別人（Q12）。
  • 並發安全：member_states.overdue_charges 是付款人名下的欠費帳單數。所有改變帳單 overdue 狀態的動作（MarkOverdue、收款、延長期限、作廢），都在同一交易內先鎖定付款人的 member_states 列，再更新計數。新預約也先鎖定同一列，再讀取計數。因此兩者必定一先一後：若欠費標記先提交，預約一定看得到；若預約先提交，代表預約當下確實還沒欠費。
  • MarkOverdue 每次只處理一張帳單，鎖序為 L1 → L2 付款人 → booking → charge，並重新確認 status = unpaid 且 due_at ≤ now。
  • 每日對帳排程：用 charges 重新計算計數，和 member_states 比對；有差異就寫入稽核並修正（雙重保險）。
  • 既有預約不會因欠費而自動取消（R1.59）；遞補遇到欠費者則跳過（6.4）。後台「欠費清單」提供「取消並遞補」，由管理員手動執行，必填原因。

6.9 出席更正稽核（v2 新增）

  • 出席紀錄只能更正，不能刪除；每次更正時，correction_reason 必填。
  • 同一交易內寫入 audit_events：attendance.corrected，內容包含 before（狀態、簽到簽退時間）、after、操作者 actor_id、時間、原因。
  • 如果更正讓爽約次數改變，下一次計算付款期限時自動反映；已建立的付款期限不會回溯變更，如需調整由管理員延長。
  • 如果更正會影響補課來源（例如 absent 改成 present），而這筆紀錄已被有效補課引用，就拒絕更正，並提示管理員先取消那筆補課。檢查時用鎖定讀取（current read），不能用快照讀取（6.12）。

已付款的預約取消後（以及「取消後才收到款項」、「重複付款」），系統會自動把 refund_state 設為 review（待退款審核），不自動退款，也不預設一定全額退款。管理員依取消政策三選一：

  • 全額退款：退款核准金額 = 可退金額，之後執行退款，完成後為 done。
  • 部分退款：輸入金額（大於 0 且小於可退金額），完成後為 partial（之後還可以再退）。
  • 不退款：refund_state 改為 declined，金額不動。

三種都必填原因，記錄處理人和時間。退款失敗時，維持 review 或 partial，不會寫入退款流水。可退金額 = amount_received − 已退款累計；重複付款的情形則只能退超出應收的部分。

6.12 補課跨場次一致性（v4 新增）

補課牽涉兩個場次：來源（原本請假或缺席的那一堂，屬於整期 S）和目標（補課的場次 E）。不增加新的表，用三條規則處理：

  1. 資料庫唯一鍵：active_flag 是 STORED generated column，定義為 IF(status IN ('confirmed','waitlisted'), 1, NULL)，並建立 UNIQUE(makeup_of_attendance_id, active_flag)。MySQL 和 MariaDB 的唯一索引都允許多個 NULL，所以「一般預約（來源為 NULL）」和「已取消的歷史補課（active_flag 為 NULL）」可以有很多筆，而有效補課每個來源只能一筆。G1 會在兩種資料庫實測插入第二筆時被拒（確認二）。不論並發有多少，同一筆請假或缺席紀錄最多只會有一筆有效補課；第二筆會被資料庫直接擋下，API 回傳 MAKEUP_ALREADY_GRANTED。
  2. GrantMakeup 的外部列鎖：L1 = 目標場次 E → L2 會員 → 最後以 FOR SHARE 依序鎖定來源 booking（整期報名）和來源 attendance，再重新確認：來源 booking 仍是 confirmed、來源 attendance 仍是 leave 或 absent。
    • 若出席更正（CorrectAttendance，L1 = 來源那一堂）先拿到 attendance 的排他鎖：GrantMakeup 會等它提交，接著讀到最新狀態；如果已改成 present 就拒絕。
    • 若 GrantMakeup 先拿到共享鎖：出席更正會等它提交，接著以鎖定讀取查到已有有效補課，就拒絕更正。
    • 若取消整期（L1 = S）先拿到來源 booking：GrantMakeup 等它提交後讀到 cancelled，就拒絕。
    持有外部列的人都不需要 GrantMakeup 已持有的鎖，因此不會形成循環等待。
  3. 取消整期後的補課清理：取消整期的交易只處理整期本身（一個 L1）。提交後，對該報名產生的每一筆有效補課，各自開一筆 CancelMakeup 交易（L1 = 補課場次），比照遞補的模式；每分鐘的排程也會掃描「來源報名已取消、補課仍有效」的資料補做，並且冪等。
  • 清理完成前的空窗期（確認三）：「有效補課」一律在讀取時判斷：補課 booking 為 confirmed，而且來源 booking 也是 confirmed。這個條件寫成同一個查詢範圍（effectiveMakeups），而且是唯一入口，以下三處都必須使用：
    • 簽到 API：來源已取消就拒絕，回傳 MAKEUP_SOURCE_CANCELLED。
    • 名額計算（6.7 的 occupied 和補課名額）：不計入。
    • 應到名單和缺席判定排程：不列入。
    因此即使清理交易還沒執行，這筆補課也不能簽到、不占名額。清理交易只是把資料狀態改成一致。

    寫入路徑同樣適用（r2 補充）：每個會改變名額或補課狀態的寫入動作，都必須在交易內重新判斷有效性，不能沿用交易開始前讀到的結果：

    • GrantMakeup：最後以 FOR SHARE 鎖定來源 booking，再確認仍是 confirmed（第 2 點）。取消整期時會因此等待，所以不可能出現「讀到有效、來源被取消、仍完成核准」。
    • 補課簽到：在簽到交易內，最後以 FOR SHARE 鎖定來源 booking，再確認仍是 confirmed。這和取消整期一定一先一後：先簽到的，簽到時來源確實有效；後簽到的會被拒絕。
    • 名額相關寫入（一般預約、補課核准、遞補）：在 L1 鎖內計算 occupied 時使用 effectiveMakeups。並發下，如果讀到來源仍有效，只是多算一席（較保守，不會超賣）；如果讀到已取消，那筆補課也已無法簽到，所以座位可以安全地讓給別人。
  • 清理範圍與鎖定：取消整期的交易提交後，查出「來源 booking = 該報名、status = confirmed」的補課，每一筆各自開一筆 CancelMakeup 交易（L1 = 補課場次 → 該補課 booking），寫入 cancel_reason = source_cancelled 和稽核。不鎖其他場次，也不回頭鎖整期。失敗由每分鐘的排程重試。
  • CancelMakeup（會員或管理員撤銷）：L1 = 補課場次 → booking 改為 cancelled → active_flag 變為 null，來源紀錄可以再被核准一次；補課名額同時釋出。補課不收費，沒有帳單。
  • 補課預約本身的出席紀錄寫在目標場次，不會反過來改動來源紀錄。

來源：使用者提供《Shared Modules 重建計畫書 Claude v4.1 定案稿2》。保留原案具體規則供 V1 對照；與 V1 最新規格衝突時，不直接覆蓋，需逐項確認。此處是規劃／參考，不代表程式已實作或驗收。

D1｜一張 bookings 表：預約對象是「整期」或「單場」，二選一

bookings.series_id 和 bookings.calendar_event_id 剛好填一個，由資料庫 CHECK 約束保證。整期報名不複製出每堂的子預約。這直接符合 EVENT-COURSE-UNIFIED-001「單場／系列只是預約模式」和 COURSE-TERM-CAPACITY-001「整期名額是唯一權威」。

效果：取消整期只需改一筆資料，不會出現「整期已取消、某堂還有效」的不一致；整期遞補也只需改一筆。

D2｜「有效預約唯一」由資料庫保證

用 MySQL／MariaDB 的 stored generated column：active_flag = IF(status IN ('confirmed','waitlisted'), 1, NULL)，再建 UNIQUE(member_user_id, series_id, active_flag) 和 UNIQUE(member_user_id, calendar_event_id, active_flag)。取消後的歷史可以保留多筆，有效預約永遠最多一筆。候補順序則用 UNIQUE(series_id, waitlist_seq) 和 UNIQUE(calendar_event_id, waitlist_seq)。

D3｜帳務：charges（應收）一對一掛在預約上，payments 是流水帳

charges.booking_id 是唯一外鍵，不再有 booking_type＋booking_id 多型關聯。收款、退款都是 payments 的一筆正數或負數，原始紀錄永不改寫。兩條獨立的狀態軸（v4）：應收 status = unpaid 未付、overdue 欠費、paid 已付清、void 作廢（未付款即取消）；退款 refund_state = none、review 待退款審核、partial 部分退款、done 已退款、declined 依政策不退。已收金額 amount_received 是流水帳加總的快取。免費預約不建立帳單（6.11）。

D4｜出席、請假、缺席、更正共用一張 attendances 表

每位預約者在每一堂（或每一場）至多一筆，唯一鍵是 (booking_id, calendar_event_id)，狀態為 present、leave、absent 三種。會員請假寫入 leave；排程在結束 1 小時後補寫 absent；管理員更正時改狀態並記錄原因。「爽約紀錄」直接從這張表計算，不另外存一個計數器，所以更正後立刻生效。

D5｜分層鎖序：每筆交易最多一個容量列，會員列一次取得

整期的動作鎖 series，單場和補課鎖 calendar_events，不會再「鎖整期之後還要逐堂鎖 N 個場次」。會員相關的鎖統一放在 member_states，在同一層一次依 user_id 排序取得；取消和遞補分成兩段交易，每次遞補只處理一人。這是降低死鎖機率的設計，不能保證完全沒有死鎖：InnoDB 偵測到死鎖時會回滾其中一筆，由交易重試 3 次處理，而每個動作都是冪等的。這一點必須用第 15 節的並發測試證明（第 7 節）。

D6｜業務動作寫成獨立的 Action 類別，API 和 Filament 共用

例如 BookSeries、BookEvent、CancelBooking、PromoteWaitlist、RequestLeave、MarkAbsences、GrantMakeup、RecordCashPayment、ExtendDueDate。每個類別負責一個動作、一個交易，並附自己的測試。Controller 和 Filament 只呼叫 Action，不直接寫資料表。

MarkOverdue、ExtendDueDateL1 → L2 {付款人} → booking → charge（每筆一張帳單）重新檢查狀態
CorrectAttendance、MarkAbsencesL1 = 出席紀錄所在的場次 → booking → attendance → auditabsence_closed_at；前後值相同就不寫入
簽到不鎖 L1；以 UNIQUE(booking_id, calendar_event_id) 新增或更新唯一鍵
為什麼這樣可以避免循環等待：任何交易都只有一個 L1，而且是第一個鎖，所以交易之間不會在 L1 互等。L2 一次依 id 排序取得，也不會在 L2 形成環。遞補一筆交易只鎖一位候補者，不會發生「拿著 A 的鎖等 B」。GrantMakeup 的外部 attendance 鎖是最後一個鎖，持有它的人（CorrectAttendance）不需要 GrantMakeup 持有的任何鎖。
這仍是推論，不是證明。安全網是：InnoDB 偵測到死鎖或鎖等待逾時時，最多重試 3 次，而且所有動作都冪等。第 15 節的並發測試 C3、C5、C6、C10、C12–C14 專門測試 ChatGPT 指出的交錯情境。

1. 模組定位

Page Atlas 是輕量的頁面索引、元件與資料關聯檢視器，不是高擬真 UI Mock、設計工具、真實 App 模擬器，也不是獨立的 Bug 管理系統。

管理員應能在短時間內：

  1. 依頁碼／名稱找到某頁。
  2. 看見該頁大致 UI、主要輸入欄位、按鈕、下拉選單與列表。
  3. 點選示意按鈕，跳到對應的下一個 Page Atlas 頁面；可返回上一頁。
  4. 查閱來源程式、主要資料表／欄位、API 與關鍵操作。
  5. 擷取簡易頁面 PNG，並一鍵複製關鍵資訊給 ChatGPT、Claude 或開發者。

不要求精準重現真實 UI 的布局、顏色、尺寸、動畫；允許合理的示意差異。只登記與定位、資料或操作相關的關鍵元件，不追求 100% 覆蓋。

2.3 Flutter 正式 App｜AdminTest 專屬頁碼顯示（P0，最小侵入）

行為與權限

  1. 一般會員、訪客、未授權管理員：不顯示頁碼；已授權測試帳號登入後自動顯示，無 App 內開關。
  2. can_view_page_ids 由 Laravel 後端透過既有登入／會員資料 API提供；不得由 Flutter 本地帳號名稱、可修改旗標或硬編碼帳密自行決定授權。此權限僅能顯示頁碼，不授予超級管理員、跨會員存取、預約／付款例外權限。
  3. 登出、切換帳號、權限資料更新時，重新套用當前帳號權限；先清除舊帳號的頁碼顯示狀態。離線時不得因權限資訊缺失而自行開啟；已登入離線情境依既有安全快取政策處理，避免跨帳號殘留。
  4. 不為 Page Atlas 額外下載頁面 Registry、Mock HTML、元件表、DB/API 索引，也不新增每頁網路請求。

畫面位置與操作安全（強制）

  • 優先在既有 Flutter Router／共用 Scaffold／頁面容器統一放置頁碼角標，避免逐頁重複實作；若架構無共同入口，才使用一個共用的 PageIdBadge 包裝元件。
  • 預設在畫面右上或右下的安全空白區顯示低對比、小尺寸、半透明頁碼；實際位置依 App 導覽列、返回鍵、浮動按鈕、底部導航及裝置安全區調整，不得固定壓在操作元件上。
  • 使用 SafeArea、必要的邊距及 IgnorePointer（或等效不攔截點擊方式），讓觸控穿透標記，不阻擋按鈕、滑動、表單、播放器、QR 掃描與系統手勢。若某頁無安全空白區，可移到既有標題列、調整位置或隱藏該頁標記，以功能可操作為最高優先。
  • 頁碼隨路由／實際畫面更新；對話框、Tab、子畫面是否另分配頁碼，以 Registry 的既定規則為準，不因視覺布局調整改變永久 ID。
  • 不提供拖曳、開關設定頁、複製按鈕、Mock 導覽或開發資訊面板；正式 App 的頁碼僅供截圖回報與人工辨識。

效能與開發成本

  • 每頁只需要頁碼常數／映射及一個共用小型文字 Widget；一般會員不建立可見標記。
  • 權限沿用既有登入資料，不額外查詢；不引入截圖、Mock、HTML 渲染或元件掃描依賴。
  • 預期安裝容量、記憶體、CPU 影響很小，實際需以 Flutter build／實機驗證，不虛報測量結果。

4. 程式碼與資料庫同步

採單向同步：Git 中的頁碼／元件 Registry（或經人工核對的 JSON Manifest）為定義來源；資料庫是供 Filament 搜尋與顯示的索引，不作為直接編輯程式的權威來源。

  1. 先盤點實際 Flutter Widget、Filament Resource／Page、路由與主要資料操作。
  2. 建立／更新輕量 JSON Manifest：頁碼、名稱、來源、關鍵元件、主要 DB／API、跳頁目標。
  3. 匯入前驗證頁碼唯一性、必要欄位、目標頁碼、來源版本及資料格式。
  4. 以資料庫交易集中更新；失敗回滾，保留上一個有效版本；相同 Manifest 重匯不得重複新增。
  5. 後台顯示最後同步 Commit／時間，避免將舊索引誤當最新正式版。

不承諾只靠掃描 Dart／PHP 就能 100% 自動取得動態元件或 API 關係。無法核實者標記「待確認」，不得猜測。初期可以人工或半自動維護 Manifest，不必建立複雜程式分析器。

7. 安全與權限

  • 完整 Page Atlas 索引／Mock／來源資訊只在經授權的 Filament 後台顯示；所有讀取 API 必須使用既有 Laravel Auth／Policy 驗證，不以 CSS 隱藏代替權限。Flutter 正式 App 只允許經後端授權的測試帳號顯示單一頁碼。
  • 僅提供安全的 Repo 相對路徑及摘要，不提供任意原始檔讀取、shell、SQL 執行或正式業務操作。
  • 示意資料使用固定合成內容，絕不讀寫正式個資／正式資料庫中的業務紀錄。
  • 頁碼與 target_page_code 只作為定位／Mock 導覽，不是授權依據。

8. 明確不做事項

  • 不追求高擬真、像素級還原、精美 UI、動畫、真實 Flutter Widget 渲染。
  • 不逐一記錄 Padding、Container、SizedBox 等純布局元件。
  • 不建立完整 UI 互動測試平台、複雜角色矩陣、真實 API 模擬器。
  • 不做自動化截圖比對、截圖版本庫、Bug 追蹤系統、完整 API／DB 依賴圖。
  • 不為此安裝 Storybook、Widgetbook、Playwright、Puppeteer、Selenium 或新的常駐服務。
  • 不重構既有 Flutter／Laravel 路由，不操作正式業務資料，不把歷史 UI Atlas 的舊頁面直接當作 V1 已實作內容。Page Atlas 所需 Migration 僅在核准的開發／測試環境執行。
  • Flutter 不增加 App 內頁碼開關設定頁、專用設定 API、額外 Page Atlas 資料同步或大型 UI 除錯套件。

9. 開發順序與驗收

第一階段（隨既有開發整合）：實際頁面盤點、永久頁碼、兩張表、最小 Manifest、來源與關鍵元件／DB／API 對照；後台顯示頁碼；Flutter 共用頁碼標記與既有登入權限整合（不做 App 內開關）。

第二階段（輕量後台功能）：Page Atlas 🔎 Tab、搜尋、元件表、簡易畫面、基本跳頁、返回、複製資訊、PNG 截圖。

唯一音樂流程

會員具單曲權限 → 點「下載」 → 取得授權與加密音檔 → 手機下載完整、驗證、寫入私有加密 Cache → 顯示「播放」 → 授權期限內可離線播放。不允許邊下載邊播放，也沒有獨立線上串流播放。

正式技術決策

  • 後台管理員單曲上傳限制 18 MiB（18,874,368 bytes），前後端雙重檢查，超限直接拒絕，不能先上傳再刪除。
  • 保留整首 AES-256-GCM、X25519、Ed25519；不做 AES-CTR、HLS、分段加密、正式 DRM。
  • 離線播放期限由後台設定，最高 365 天；完整下載且授權有效才能播放。
  • 刪除伺服器解密線上串流、5 分鐘線上播放 URL、4-slot 串流並發限制、串流 503 retry 與 Range 開發；保留加密檔下載、其短效 cipher URL、本機 seek 與影片連結。
